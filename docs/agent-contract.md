# 에이전트 작업 협약

AI 상담(C안, #110)을 나눠 만들 때 지킬 약속이다. 규칙 원문은 AGENTS.md 4절이고, 누가 맡는지는 이슈 담당자로 정한다.

## 1. 역할

- 오케스트레이터: 고객과 말하는 LLM 하나. 의도 라벨에 맞는 역할로 답하고, 필요하면 도구 · 공종 에이전트를 불러 한 답으로 합친다. 되묻기는 오케스트레이터만 한다.
- 공종 에이전트(`trade`): 고객에게 말하지 않는 하위 호출. 공정별 설정 + 지식 검색으로 필요한 조건 · 주의점 · 근거 번호를 돌려준다.
- 범위 밖: LLM 없이 고정 안내.
- 의도 라벨 `trade`(옛 이름 `consult`)는 공정 상담 역할이다. 학습 데이터 · eval · 모델 라벨도 `trade`다(#75).

| 의도 라벨 | 역할 | 하는 일 | 지시문 |
| --- | --- | --- | --- |
| `orchestrator` | 가이드 | 처음 궁금증 · 시작 순서 · 기본 정보 · 제출 서류, 복합 요청 | `v2/prompts/guide_v*.md` |
| `trade` | 공정 상담 | 우리 집 조건 묻기 · 공정 간 조정. 공종 에이전트를 부른다 | `v2/prompts/trade_v*.md` |
| `quote_explanation` | 견적 설명 | 계산 엔진 금액 풀이만 | `v2/prompts/quote_explanation_v*.md` |
| `schedule` | 공정표 | 말을 제약으로 바꾸기 · 결과 설명. 일정 MCP | `v2/prompts/schedule_v*.md` |

- 지금은 가이드 · 공정 상담이 `chat_v1.md` 하나를 같이 쓴다. 나누는 것은 eval을 붙인 `prompt` PR로 한다.
- 역할마다 쓸 수 있는 도구는 `v2/ask_tools.py`의 `BY_KIND`가 정한다.

## 2. 파일 나누기

| 묶음 | 고치는 파일 |
| --- | --- |
| 한 턴 · 관문 | `v2/ask.py` · `v2/guard.py`, `agent/gate.py` · `route.py` · `intent.py`, `evaluation/intent` |
| 가이드 | `v2/prompts/guide_v*.md`(지금 `chat_v*.md`), `evaluation/guide` · `orchestrator` |
| 공종 | `agent/trade_agent.py` · `trades/dobae.py` · `trades/mokgong.py`, `v2/prompts/trade_v*.md`, `evaluation/trade` |
| 견적 설명 (담당 미정) | `v2/prompts/quote_explanation_v*.md`, `evaluation/quote_explanation` |
| 공정표 | `v2/prompts/schedule_v*.md`, `mcp_server.py`, `evaluation/schedule` |
| 지식 검색 · 추천 질문 | `knowledge/`, `evaluation/rag` · `answer` |
| 대화 저장 | `chat/` |
| 공용 | `agent/schemas.py` · `llm.py` · `trades/base.py`, `v2/ask_tools.py` · `v2/schemas.py`, `config.py` |

- 자기 묶음 파일만 고친다.
- `trades/base.py`(공정 설정 모양)는 공종 · 견적 설명 · 공정표가 같이 읽으므로 공용이다. 공정별 값은 공종이 맡는다.
- 공용 파일은 여럿이 같이 쓰므로 충돌을 줄이려고 이렇게 고친다:
  1. 고칠 게 생기면 팀 채팅에 먼저 말한다.
  2. 새 줄 더하기만이면 기능 PR에 같이 둔다. PR 본문에 고친 공용 파일을 적는다.
  3. 기존 줄을 바꾸거나 지우면 그 변경만 담은 PR을 따로 올려 먼저 병합한다.
  4. 나머지는 dev로 rebase해서 받는다.
- `agent/graph.py` · `orchestrator.py` · `quote_explanation_agent.py` · `schedule_agent.py` · `extract.py`는 C안에서 쓰지 않는다. 정리는 따로 한다.

## 3. 공종 에이전트 모양

- 받는 값: 오케스트레이터가 나눈 고객 문장, 코드가 고른 공정 설정(도배 · 목공, 모르면 둘 다), 지식 검색 결과(조각 번호 포함). 사용자 · 대화 id는 받지 않는다.
- 돌려주는 값(Pydantic): 공정, 필요한 조건(빠진 칸), 주의점, 근거 번호. 금액 · 수량 · 날짜는 넣지 않는다.
- 설정 + 검색으로 채울 수 있으면 LLM을 부르지 않는다. 필요할 때만 작은 모델을 쓴다.
- LLM 실패(`llm.LLMError`)는 잡아서 그 공정 몫만 실패로 돌려준다. 규칙으로 만든 가짜 설명으로 채우지 않는다.
- 다른 에이전트 · 오케스트레이터를 부르지 않는다.

## 4. LLM 호출과 출력 모델

- 오케스트레이터는 `llm.chat_tools(system, messages, tools)`로 부른다. 지시문 · 도구 · 반복 횟수는 서버(`v2/ask.py`)가 정한다.
- 공종 에이전트는 `llm.structured(role, schema, messages)`로 부른다.
- LLM에서 받는 모양(예: `TradeNote`)은 자기 파일 안에 둔다. 여럿이 같이 쓸 때만 `agent/schemas.py`로 옮긴다.
- 답 글은 출력 검사(`v2/guard.py`)를 거친다. 금액 · 기간 숫자는 계산 엔진 결과에 있어야만 남는다.

## 5. 오케스트레이터가 공종 에이전트를 부를 때

- 서버 도구로 부른다. 두 공정이면 동시에 부른다.
- 턴당 공종 에이전트 호출은 3회까지, 역할별 도구 호출은 4회까지다.
- 돌아온 주의점은 바꾸지 않고 근거 번호를 붙여 보여 준다.
- 일부 공정만 실패하면 그 몫만 "설명을 만들지 못했어요"로 넣는다. 모두 실패했을 때만 답 전체를 실패로 한다.

## 6. 데이터와 도구

- 도구는 `v2/ask_tools.py`가 정한다. 서버 도구(계산 엔진 · 지식 검색 · 공종 에이전트 · 공정표 조건)는 서버가 실행하고, 화면 도구(고객 상태 저장 · 단계 카드)는 브라우저가 실행해 결과만 돌려준다.
- 숫자 근거는 서버가 만든 값(계산 엔진 결과 · 서버가 다시 읽은 근거 원문)만 쓴다. 브라우저가 보낸 글은 근거로 믿지 않는다.
- 견적 · 공정표 정보는 화면이 보낸 입력으로 서버가 다시 계산한다. 기능 service는 import하지 않는다.
- 일정 MCP는 공정표 역할만 부른다.
- 업체가 쓴 글은 지시문에 넣지 않고 데이터로만 넘긴다.

## 7. 테스트와 eval

- 테스트는 `backend/tests/test_v2_ask.py` · `test_agent_<묶음>.py`. `llm.set_stub` · `set_jev_stub`으로 답을 정하고 `LLM_LIVE=false`로 돈다.
- eval 세트는 `evaluation/<묶음>/`에 두고 dev와 held-out을 2:1로 나눈다.
- 프롬프트를 바꾸는 PR은 커밋 type `prompt`로 하고 eval 결과를 붙인다.

## 8. 한 턴 (`/v2/ask`)

`v2/ask.py`가 한 턴을 돌리는 순서다.

| 순서 | 하는 일 | DB 세션 |
| --- | --- | --- |
| 1. 열기 | `chat_id`로 내 대화를 연다(`get_for`, 없으면 새로 만든다). 남의 대화 · 없는 대화는 404. `rev` · `waiting` · 지난 대화(`recent`)를 들고 간다 | 짧은 세션, 닫고 나온다 |
| 2. 관문 | `gate.classify(message, waiting)`. 범위 밖은 고정 안내, 버튼은 의도를 같이 보내 관문을 건너뛴다 | 없음 |
| 3. 실행 | 역할 지시문 + 지난 대화 + 이번 질문으로 LLM ↔ 도구. 화면 도구를 부르면 턴(`rev` 포함)을 Redis에 두고 응답하고, 결과가 오면 이어 간다 | 쥐지 않는다 |
| 4. 검사 | 출력 검사(`v2/guard.py`): 숫자 · 근거 · 금지 표현 · 가림 | 없음 |
| 5. 저장 | `rev`가 그대로일 때만 1 올리고 고객 문장 · 답 · 관문 결과 · `waiting`을 쓴다(`save_turn`). 다르면 아무것도 쓰지 않고 409 | 새 세션, commit |
| 6. 응답 | 답 · 근거 · 추천 질문 · `chat_id`. commit 뒤에만 보낸다 | 없음 |

**넣는 값**

| 값 | 어디서 | 비고 |
| --- | --- | --- |
| `user_id` | 로그인 세션 | 요청 본문 · LLM 출력으로 받지 않는다 |
| `chat_id` | 요청 본문(없으면 새 대화) | 남의 대화면 404 |
| `message` | 요청 본문 | 본문 한도는 `BodyLimit` |
| 지난 대화 | `recent()`의 최근 메시지 | 이번 문장은 빼고 오래된 것부터 |
| `waiting` | 대화 행에 저장해 둔 지난 턴 값 | 없으면 `None` |
| `intent` | 버튼(`Choice.intent`)을 눌렀을 때만 | `source="button"`. 관문이 다시 분류하지 않는다 |
| 견적 · 공정표 입력 | 요청 본문 | 서버가 계산 엔진으로 다시 계산한다 |

**저장**

- 고객 문장과 답을 메시지 행 두 개로 쌓는다(같은 `turn`). 답은 화면에 보낸 글 그대로 저장한다
- 관문 결과(라벨 · 신뢰도 · 출처)는 고객 문장 행에만 남긴다. 의도 eval 재료
- 대화 행에 `waiting`을 덮어쓰고 `rev`를 1 올린다. 이번 턴에 되물은 역할이 있을 때만 `waiting`에 그 라벨이 들어간다

**응답 모양**

- `V2AskOut`: 답 글, 근거 목록(출처만), 추천 질문 0~3개, 뺀 문장 수, `chat_id`
- 지금은 답을 한 번에 보낸다. 글자 단위 흘려보내기는 나중에 더한다

**동시 요청: 번호표(`rev`)**

- 대화 행의 `rev`(정수, 1부터). 열 때 본 값을 들고 있다가, 저장할 때 `rev`가 그대로일 때만 조건부 UPDATE로 1 올린다. 1행이 아니면 409이고 메시지도 쓰지 않는다
- 만료 시각으로 잠그지 않는다. 한 질문이 요청 여러 번(화면 도구 재개)에 걸치고 화면이 중간에 버릴 수 있어서, 기한 잠금은 버린 질문이 대화를 막는다
- 같은 대화에 두 질문이 동시에 오면 둘 다 실행되고 먼저 저장한 쪽만 남는다. 늦은 쪽 LLM 호출은 버려지므로 사용자별 요청 제한으로 비용을 막는다
- 예외가 나도 풀 잠금이 없다. 저장하지 않고 오류를 보낸다

- 가이드 · 공정 상담 지시문을 `chat_v1.md`에서 나누는 시점
