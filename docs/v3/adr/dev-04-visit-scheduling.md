# dev-04 실측 일정 모델 · 기한: visits 상태를 늘리고, 반나절 잡기 표 + jobs 예약 수거

- 날짜: 2026-11-18 · 쓴 역할: 개발자
- 관련 화면 · 이야기: C13~C22 · C28 · C30 · C32 · C61 · D03 · D08 · D14~D17 · V03~V08 · V20, J3 · J5 · J6 · J11 · J12 · J14 · J19, 9판 D08 · D09 · D10 · D14 · D15 · D19 · D29, rules.due · 관련 코드: `backend/app/visit/`, `backend/app/calc/schedule.py`, 새 `backend/app/jobs/`, `backend/app/worker.py`

## 배경

v3는 '연결만'을 버리고 믿집이 실측 날짜를 중계해요. 요청(+48시간 답) → 업체 기간 · 빼는 날 · 바로 확정 → 고객 반나절 고르기(+7일) → 바로 확정이면 확인 창 뒤 확정, 아니면 업체 수락(+48시간, 그동안 반나절을 잡아 둠) · 다른 날 제안(+48시간) → 확정 → 전날 18:00 알림 → 실측 받음 → 견적서(실측 + 3일 18:00). 같은 업체의 같은 반나절을 두 고객이 거의 같이 고르면 늦은 쪽은 막혀야 해요(C16). D14 A는 '기한마다 jobs 예약 일 + worker'로 정했어요.

## 대안

| 안 | 내용 | 좋은 점 | 걸리는 점 |
| --- | --- | --- | --- |
| A | `visits.status`를 늘리고(requested → offered → picked/proposed → booked → visited → quoted → chosen + 끝 상태), 업체 기간 · 반나절 잡기 · 제안 · 바꾸기를 작은 표로. 반나절은 `visit_holds` 부분 UNIQUE로 겹침을 DB가 막아요. 기한은 `jobs`(run_at) + 1분 수거, 화면 '지남'은 계산으로 | 화면 카드 상태와 1:1 · 겹침을 DB 제약으로 막음 · worker가 늦어도 화면은 맞음 | 상태가 많아 전이 표 테스트가 길어요 |
| B | 일정 협의를 '제안' 한 표에 이벤트로만 쌓고 상태는 읽을 때 계산 | 표가 적음 | 겹침을 제약으로 막기 어렵고, 기한 처리 조건부 UPDATE가 복잡해요 |
| C | 기한을 arq 지연 작업(`_defer_until` + `_job_id`)으로만 | 정확한 시각 | Redis가 지워지면 기한이 사라져요(Redis는 지워져도 되는 것만). arq는 유지보수 전용 |
| D | 기한을 화면 계산으로만(상태는 그대로) | worker 없음 | 칸 비우기 · 알림 · 반나절 풀기를 아무도 안 해요(D14 A와 달라요) |

## 고른 것과 이유

- 고른 안: **A**(기한은 A의 jobs + 화면 계산 함께).
- 이유
  - 반나절 겹침은 '같은 업체 · 같은 날 · 같은 반나절에 살아 있는 잡기 1개'라는 부분 UNIQUE로 막아요. 늦은 쪽은 IntegrityError → 409 `slot_taken`('방금 다른 고객이 골랐어요')이 돼요. 지금 코드의 '칸 부분 UQ → 409'와 같은 방식이에요.
  - 기한 일은 같은 트랜잭션에 `jobs` 행으로 남겨요(아웃박스, S23). worker가 1분마다 `run_at <= now()`인 행을 `FOR UPDATE SKIP LOCKED`로 가져가요(S24). arq `cron(unique=True)`이 여러 worker에서도 한 번만 돌려요(S21). Redis가 비어도 행은 DB에 남아요.
  - 처리는 멱등이에요: '아직 그 상태이고 기한이 지났을 때만' 조건부 UPDATE, 알림은 `dedup_key`. 이미 답했으면 아무것도 하지 않아요(D14 A 문구 그대로). 같은 일이 두 번 돌아도 결과가 같아요(S23).
  - 화면은 상태 + `*_due_at` + 지금 시각으로 '지남'을 계산해서(계산 엔진) worker가 몇 분 늦어도 틀리게 보이지 않아요(팀 확인 20 'worker가 멈추면 기한이 밀려요'의 화면 쪽 답).
  - arq는 유지보수 전용이라(S22) 지연 작업 기능에 기대지 않고 cron 하나와 함수만 써요. 나중에 순수 asyncio 고리로 바꾸기 쉬워요.

## 정한 세부 (자세히는 `data-model.md` 4장)

- 기한(계산 엔진 `calc/deadline.py`): 업체 첫 답 = 보낸 때 + 48시간(D15 C) · 고르기 = 업체 답 + 7일(D09) · 수락 = 고른 때 + 48시간(D10) · 제안 고르기 = 제안 + 48시간 · 바꾸기 답 = 요청 + 48시간 · 견적서 = 실측일 + 3일 18:00(D19, 지금 `due_at`) · 공사 날짜 = 확정 + 2일 18:00(그대로) · 다른 날짜 요청 답 = 요청 + 48시간(지금 다음 날 18:00에서 바꿈) · 공사 끝 확인 = 알린 뒤 7일, 3일 전 알림(D24).
- 반나절: `am`(오전) · `pm`(오후). '실측 시각 지남'(C32)은 오전 13:00 · 오후 18:00 뒤로 정해요(계산 엔진 상수, 팀 확인).
- 바로 확정(I5): 업체가 답할 때 켠 값(`visit_windows.instant`)이 기준이에요. 업체 기본값(`vendors.instant_default`)은 목록 배지와 토글 처음 값에만 써요. 팀 확인 2(사람이 누른 확정으로 볼지)는 그대로 열려 있어요.
- **D12 보류의 최소 처리(팀 확인 필요)**: 수락 기한 · 제안 기한이 지나면 잡아 둔 반나절만 풀고 '날짜 고를 차례'로 되돌려요(고르기 기한이 지났으면 '기한 지남'). 칸은 비우지 않아요. 업체 첫 답이 없을 때만 칸이 비어요(8판 그대로).
- 다시 요청: 같은 업체에 두 번까지(`visits.attempt` 1~2, UNIQUE). 두 번째도 답이 없으면 그 업체는 이 공사에 못 담아요(C18).
- AI 초안(D03 · D08): 희망 기간은 계산 엔진이 공사 시작 희망일 − 28일 ~ − 14일로 만들어요(UC-VIS-01). 날짜 추천(D15 '1.4(월) − 20일 = 12.15(화)')도 계산 엔진 함수예요. AI는 설명 · 카드만 만들고 보내기 · 확정은 고객이 눌러요.
