# design-02 토큰 구조와 색: 3층 토큰 · 흰 바탕 기본 · 대비를 맞춘 B 팔레트

- 상태: 고름 · 바탕색 한 가지는 **사용자 확인 필요**
- 날짜: 2026-11-18 · 쓴 역할: 디자이너
- 관련 화면 · 이야기: 9판 화면 109개 전부 · 관련 코드: `frontend/app/globals.css`(v2 토큰), `components/v2/v2.module.css`, 초안 `docs/v3/design/tokens.draft.css`

## 배경

9판 B 시안은 토스 TDS 팔레트를 그대로 썼고(회색 바탕 #F2F4F6 + 흰 묶음 + 파랑 #3182F6), 지금 코드는 v2 '흰 바탕 · 서류형' 토큰이에요. 같은 짝을 계산하면 9판 값은 84짝 중 40짝이 대비 기준을 못 넘어요(보조 글자 3.04:1, 파랑 단추 흰 글자 3.71:1, 입력 칸 경계 1.10:1 등). 제작을 나눠 하기 전에 토큰 이름 · 층 · 값을 하나로 정해야 해요.

## 대안

| 안 | 내용 | 좋은 점 | 걸리는 점 |
| --- | --- | --- | --- |
| A | 지금 v2 평평한 토큰(`--ink` · `--accent` …)에 9판 값을 덮어씀 | 옮길 것이 적어요 | 역할 이름이 섞여(`--surface`가 바탕 · 고른 것 둘 다) 화면마다 뜻이 달라요. 9판 대비 문제를 그대로 가져와요 |
| B | **3층(기본 → 의미 → 컴포넌트) · 믿집 값 · 대비를 계산해 맞춤** | 화면은 의미 이름만 써서 값을 바꿔도 한곳만 고쳐요. 회색 바탕 · 나중 어두운 화면도 2층만 바꿔요. DTCG 안정판과 같은 생각 | 처음에 이름을 많이 정해야 해요. 옛 이름 별칭 기간이 있어요 |
| C | TDS 값을 그대로 쓰고 대비가 모자란 곳만 고침 | 9판 모양에 가장 가까워요 | TDS 자료는 앱인토스 범위 안에서만 쓰게 돼 있어요. '토스 따라 하기'로 보이는 B의 아쉬운 점이 커져요 |
| D | Tailwind 같은 도구 토큰 | 도구가 많아요 | 지금 코드는 CSS Modules라 큰 이사예요(지시문 범위 밖) |

## 고른 것과 이유

- 고른 안: **B**.
- 이유
  - 층: 1층 기본 값은 2층만 가리키고, 화면은 2 · 3층만 써요(간격 `--mj-space-*`만 예외). 테마(밝게 · 어둡게)는 별칭 층에서 바꾸는 것이 표준 구조예요(근거 1). KRDS도 역할별 이름 + 단계로 나눠요(근거 2).
  - 팔레트: 9판의 색상각(파랑 216° · 회색 214°)은 그대로 두고, **단계마다 흰 바탕 대비가 정해진 값**이 되게 믿집 값을 새로 만들었어요(예: 500 = 3.5:1, 600 = 5.33:1). KRDS의 '단계 숫자가 대비를 말한다' 방식이에요(근거 2). TDS 자료는 앱인토스 범위 안에서만 쓰게 돼 있어 값을 그대로 옮기지 않았어요(근거 3).
  - 대비: 글자 4.5:1 · 테두리 · 아이콘 · 상태 3:1(근거 2 · 5 · 6). 누를 곳은 44(최소 40)로 WCAG 2.5.8의 24보다 크게 둬요(근거 4). 9판에서 고친 것: 주 색 #3182F6 → #1B66D8, 가장 옅은 글자 #8B95A1 → #616C7B, 입력 칸에 1px 테두리(gray-500, 3.5:1 — 테두리 없는 입력은 바탕끼리 3:1이어야 해서, 근거 5), 체크 · 스위치 끔 · 끌어다 놓기 테두리 gray-300 → gray-500, 배지 글자를 700 단계로, 별 #FFB800 → #C48200, 제안한 날 주황 #E07B00 → #B35900, 공휴일 글자 → red-700(업체 띠 위에서도 4.78:1).
  - 상태: 색은 작은 아이콘에만, 글자가 늘 함께(N4 C). 색만으로 알리지 않아요(근거 2 · 7).
  - **바탕**: 기본은 흰 바탕(사용자 기존 결정 '흰 바탕 · 서류형', v3 고르기 판 바탕 규칙에도 적혀 있어요). 흰 바탕에서는 묶음에 1px 줄(`--mj-group-edge`)을 둬서 9판 묶음 모양을 그대로 살려요. 9판처럼 회색 바탕 + 흰 묶음(테두리 없음)은 `<html data-canvas="gray">` 한 줄로 바뀌고, 두 모드 모두 83짝이 대비를 넘어요. → 사용자가 9판(B)을 보고 잠정으로 골랐으니 **어느 쪽을 기본으로 할지 사용자 확인 필요**. 확인 전에는 기존 결정(흰 바탕)으로 만들어요.
  - 어두운 화면: 1차는 안 해요. 보통 시력에는 밝은 화면이 대체로 낫고 작은 글씨일수록 그래요(근거 8). 믿집은 짧은 일 · 숫자 서류가 많고, B 회색 묶음은 어두운 화면에서 다시 손봐야 해요(디자인 방향 판 B 아쉬운 점). 안드로이드 크롬이 멋대로 어둡게 바꾸지 않게 `color-scheme: only light`를 둬요(근거 9). 나중에 하면 2층만 바꿔요(KRDS '선명한 화면 모드'처럼 사용자가 고르게, 근거 2).
  - 글자 크기: 일곱 단계(13 · 14 · 16 · 18 · 20 · 28 · 38)는 사용자 결정이라 rem 토큰으로만 둬요. 9판 26가지 크기를 일곱으로 모았고(design-system 2.3), W1 A 설명의 웹 제목 22px는 20px로 맞춰 **사용자 확인 필요**로 적었어요.

## 근거 (직접 열어 확인한 것만)

1. DTCG 첫 안정판 — https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/ (확인 2026-11-18) — 2025.10 안정판, 별칭 · 상속 · 밝게/어둡게 테마, W3C 커뮤니티 그룹 보고서
2. KRDS 색 — https://www.krds.go.kr/html/site/style/style_02.html (확인 2026-11-18) — 역할 + 단계 이름, 단계 숫자 = 대비(40 = 3:1 · 50 = 4.5:1 · 70 = 7:1 · 90 = 15:1), 입력 테두리 50, 상태는 색만으로 알리지 않음, 강조색 5% 이하, 선명한 화면 모드
3. 앱인토스 디자인 컴포넌트 — https://developers-apps-in-toss.toss.im/design/components (확인 2026-11-18) — 제공 자료의 지식재산권은 토스, 앱인토스 범위 안에서만 사용
4. WCAG 2.2 2.5.8 이해 — https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html (확인 2026-11-18) — 누를 곳 24×24 AA, 44×44는 2.5.5
5. WCAG 2.2 1.4.11 이해 — https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html (확인 2026-11-18) — 테두리 없는 입력은 바탕끼리 3:1, 체크 테두리 3:1, 고른 상태 표시 3:1, 꺼진 것은 예외
6. 서울시 누리집 접근성 기준 — https://news.seoul.go.kr/gov/archives/47485 (확인 2026-11-18) — 한국형 웹 콘텐츠 접근성 지침 2.2(방송통신표준심의회, 2022.12.28)
7. Carbon 상태 표시 — https://carbondesignsystem.com/patterns/status-indicator-pattern/ (확인 2026-11-18) — 색만으로는 안 됨, 색 · 모양 · 기호 중 둘 이상, 상태 색 3:1
8. NN/g 어두운 화면 — https://www.nngroup.com/articles/dark-mode/ (확인 2026-11-18) — 보통 시력엔 밝은 화면이 대체로 나음, 작은 글씨일수록, 기본은 밝게 두고 고를 수 있게
9. Chrome 자동 어둡게 — https://developer.chrome.com/blog/auto-dark-theme (확인 2026-11-18) — `<meta name="color-scheme" content="only light">` 또는 `:root { color-scheme: only light }`로 빠짐
10. TDS Mobile 색 — https://tossmini-docs.toss.im/tds-mobile/foundation/colors/ (확인 2026-11-18) — 9판이 쓴 grey · blue 값의 출처(견줌용)

## 검증

- 방법: `python docs/v3/design/check_contrast.py`(토큰 파일을 읽어 var()를 풀고 83짝 대비 · 글자 크기 단계 · 누를 곳 크기를 봄), `--nine`으로 9판 값 견줌, `--md`로 표.
- 결과(2026-11-18 실행, verification/design.md)
  - 흰 바탕 83짝 · 회색 바탕 83짝: 실패 0. 가장 아슬한 짝은 `--mj-line-control` / `--mj-fill` · `--mj-bg`(회색) 3.15:1(기준 3:1).
  - 9판 값: 84짝 중 40짝 실패(가장 낮은 것 입력 칸 경계 1.10:1).
  - 글자 크기: 1층 · 2층 모두 일곱 단계 안. 누를 곳 토큰: 모두 40 이상(기본 44).
  - 화면에서의 대비(실제 렌더링)는 제작 뒤 axe로 다시 봐요 → 검증 대기.
